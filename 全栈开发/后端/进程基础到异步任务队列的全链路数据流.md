# 全栈后端核心概念总结

> 学习时间：2026-07-17 ~ 2026-07-19  
> 主题：从进程/端口基础到异步任务队列的全链路数据流

---

## 一、基础概念：进程、端口、文件

### ✅ 已掌握

- **进程是活的，文件是死的**：硬盘上的文件（如 `main.py`、`index.html`）必须由运行中的**进程**读取并响应，无法“直接访问文件”。进程杀掉 → 服务不可访问。
- **端口是进程的门牌号**：`IP:端口` 定位一个唯一的应用程序。Nginx 监听 443（对外），FastAPI 监听 8000（内网），同一个 Nginx 进程可以基于 HTTP 请求头的 `Host` 字段，将请求转发到不同后端或静态文件目录。

---

## 二、进程、线程、协程与 CPU 的关系

### ✅ 已掌握

- **CPU 是演奏家，进程是总乐谱，线程是分谱，协程是跳转记号**。
- **进程是资源容器**（内存、文件句柄），**线程是 CPU 调度的最小单位**。
- **单线程 + 事件循环 + 协程** 可以支撑高并发（如 FastAPI + uvicorn）。

### ⚠️ 重点纠正

- **并非所有函数都是协程**：只有 `async def` 定义的函数才是协程函数，调用后返回协程对象。普通 `def` 函数事件循环无法介入调度。
- **`async` 不是空声明**：它改变了函数的返回类型（返回协程对象）和执行方式（必须被 `await` 或事件循环调度才执行）。

---

## 三、async/await 工作原理

### ✅ 已掌握

- **`await` 是主动让路点**：当前协程挂起，控制权交还事件循环，事件循环去执行其他协程。I/O 完成后协程被唤醒，进入就绪队列等待再次被调度。
- **`await` 后面必须是可等待对象**（协程、实现了 `__await__` 的对象），意味着这个操作是“等别人干活”（网络、磁盘、定时器）。

### ⚠️ 重点纠正

- **`async def` 内不用 `await` 是灾难**：函数照样阻塞执行，事件循环被卡死，`async` 标签无效。
- **CPU 密集型函数不应放在异步流程里**：因为它是“自己算”而非“等别人”，不会主动让路。正确做法是交给**子线程**（`run_in_executor`）或**独立进程**（Celery Worker）。

### ❌ 常见误区（已澄清）

| 误区 | 真相 |
|------|------|
| `async` 只是个声明符号 | 它改变了函数的返回类型和执行方式 |
| `async` 函数 = 异步不阻塞 | 内部没有 `await` 照样阻塞 |
| `await` 后面放什么都会异步 | `await` 普通函数无效，照样阻塞 |
| 操作系统会自动判断函数类型 | 操作系统只看指令，不识别业务类型 |

---

## 四、CPU 密集型 vs I/O 密集型

### ✅ 已掌握

- **判断标准**：函数是在“自己算”（CPU 密集型）还是“等别人”（I/O 密集型）——**完全由程序员根据业务逻辑判断，操作系统不参与**。
- **CPU 密集型**：矩阵运算、模型推理、图像处理 → 丢给线程池或 Celery Worker。
- **I/O 密集型**：数据库查询、HTTP 请求、文件读写 → 用 `async/await`。

### 实践选型表

| 耗时 | 类型 | 方案 |
|------|------|------|
| <1秒 | 轻量 CPU | 普通 `def`，放 `async` 里也行 |
| 1-10秒 | 较重 CPU | `loop.run_in_executor()` 线程池 |
| >10秒 | 重量 CPU/GPU | Celery 异步任务队列 |

---

## 五、操作系统挂起机制 vs 协程挂起机制

### ⚠️ 关键区分（易混淆）

| | 操作系统挂起 | 协程挂起 |
|---|---|---|
| 挂起对象 | **线程/进程** | **协程** |
| 触发条件 | 系统调用（I/O）阻塞 | `await` 一个异步对象 |
| 调度者 | 操作系统内核 | 用户态事件循环（asyncio） |
| 操作系统是否感知 | 感知（线程状态变为阻塞） | **不感知**（线程看起来一直在运行） |
| 代价 | 高（上下文切换） | 低（用户态切换） |

### 核心结论

**`await` 一个 CPU 密集型函数 = 让操作系统的“自动挂起”和用户态的“主动让路”同时失效**，因为线程未阻塞（操作系统不挂起），协程也不让路（没有 `await`），导致双重灾难：整个服务假死。

## 六、异步任务队列（Celery）

### 架构三要素

| 角色 | 实现 | 职责 |
|------|------|------|
| **生产者** | FastAPI 进程 | 收到请求，生成任务ID，扔消息到 Broker，立刻返回 202 |
| **消息代理（Broker）** | **Redis**（不是 Celery！） | 暂存任务消息，FIFO 队列 |
| **消费者** | Celery Worker 进程 | 从 Broker 取任务，执行 CPU/GPU 密集计算，更新状态/结果 |

### ⚠️ 重点纠正

- **Celery ≠ Redis**：Celery 是异步任务框架，Redis 是它使用的消息代理。`Producer → Broker(Redis) → Consumer(Celery Worker)`。
- **Celery Worker 是客户端，不开端口**：它主动连接 Redis:6379，不需要自己监听端口接收请求。

### 进度上报机制

```python
@celery_app.task(bind=True)
def run_ai_diagnosis(self, image_path):
    self.update_state(state='PROCESSING', meta={'progress': 30, 'stage': '预处理中'})
    # ... 干活 ...
    self.update_state(state='PROCESSING', meta={'progress': 60, 'stage': 'AI推理中'})
    # ... 干活 ...
    return final_result
```

前端通过轮询 `GET /diagnosis/{task_id}`，FastAPI 用 `AsyncResult(task_id).info` 查 Redis，返回进度。

### 结果生命周期

- 任务消息：Worker 取走即删。
- 任务状态/结果：默认保留 24 小时（`result_expires=86400`），自动过期清除。
- **Redis 是“临时速记本”**，永久数据存 MySQL/PostgreSQL。

## 七、Redis 的数据存储方式

### 核心原则

**Redis 只认字符串（字节序列）。** Python 对象必须先**序列化**成字符串才能存，取出后**反序列化**恢复。

### Celery 默认用 JSON

- `update_state(meta={...})` → Celery 自动 `json.dumps()` 存入 Redis
- `AsyncResult().info` → Celery 自动 `json.loads()` 恢复

### 常用序列化方式

| 方式 | 特点 |
|------|------|
| JSON | 跨语言通用，Celery 默认，不能存 `datetime`/`bytes` |
| Pickle | 任意 Python 对象，但不安全，不推荐 |

### Key 设计原则

**根据查询需求主动设计**，没有固定结构：

| 数据 | Key 示例 |
|------|---------|
| 任务状态 | `task:abc-123:status` |
| 用户最近任务 | `user:p001:tasks` |
| 会话 Token | `session:{token}` |
| 限流计数 | `rate_limit:doc001:2026-07-19` |

## 八、AI 医疗平台全链路数据流（全景）

```
浏览器 ──HTTPS──▶ Nginx:443 ──HTTP──▶ FastAPI:8000 ──.delay()──▶ Redis:6379
  ▲                    ▲                    │                        │
  │                    │               [保存影像]              [Celery Worker
  │                    │               [写数据库]               主动拉取任务]
  │                    │                    │                        │
  │                    └────── 返回 202 ────┘               [GPU推理 30秒]
  │                                                                  │
  │  轮询 GET /diagnosis/{task_id}                                    │
  ├────────▶ Nginx ──▶ FastAPI ──查 Redis──▶ 返回进度/结果            │
  │                                                    │              │
  └──────────────────── 返回结果 ──────────────────────┘              │
                                                                      │
                                              [写结果到 Redis + 数据库]
```

### 各进程职责总结

| 进程 | 端口 | 类型 | 角色 |
|------|------|------|------|
| Nginx | 443（对外） | I/O 密集 | TLS终结、静态文件、反向代理 |
| FastAPI | 8000（内网） | I/O 密集 | 业务逻辑、任务分发、结果查询 |
| Redis | 6379（内网） | I/O 密集 | 消息队列（Broker）+ 结果缓存（Backend） |
| Celery Worker | 无端口 | CPU/GPU 密集 | 加载模型、执行推理 |

## 九、防御性编程要点

### Worker 崩溃防护

- **`try...except` 包裹可能出错的代码块**，防止单个坏任务搞崩整个 Worker。
- **Supervisor / Docker `restart: always`**：Worker 万一崩溃，自动重启。

### 监控告警

- **队列积压监控**：Redis 队列长度超过阈值 → 报警。
- **心跳检测**：用 Supervisor 或 Flower 监控 Worker 在线状态。
